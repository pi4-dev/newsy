## Raport technologiczny

### Technologia

#### Cloudflare buduje publiczne CA z natywną ścieżką do post-quantum WebPKI

Cloudflare ogłosił zamiar uruchomienia własnego publicznego Certificate Authority i złożył wnioski do root programów Chrome, Apple, Microsoft i Mozilla. Równolegle podpisał umowę zakupu istniejącego, szeroko zaufanego materiału root CA od GlobalSign, aby skrócić drogę do powszechnej kompatybilności. Nowe CA ma obsługiwać klasyczne certyfikaty oraz Merkle Tree Certificates jako ścieżkę do skalowalnego PQ authentication.

**Znaczenie:** post-quantum migration przestaje dotyczyć wyłącznie key exchange i zaczyna obejmować cały WebPKI: CA, CT, browser root stores i handshake size. MTC grupuje wiele certyfikatów pod jednym podpisanym rootem Merkle i wykorzystuje inclusion proofs zamiast klasycznych, ciężkich chainów; przy podpisach PQ, które są wielokrotnie większe od klasycznych, ogranicza to koszt transportu i logowania. W eksperymencie Chrome medianowy handshake z MTC był o 9% szybszy od klasycznego chainu w testowanej konfiguracji.

**Źródła:** https://blog.cloudflare.com/cloudflare-certificate-authority/ ; https://blog.cloudflare.com/pq-ca-with-mtcs/

### Biznes

#### Vultr składa HPE zamówienie za 1,2 mld USD na AMD Helios

HPE ogłosił pierwsze duże zamówienie na AMD Helios AI Rack by HPE: Vultr wdroży systemy o wartości 1,2 mld USD w swoich amerykańskich data centers. Pojedynczy rack integruje 72 AMD Instinct MI455X, EPYC „Venice”, Pensando Vulcano AI NICs i ROCm; scale-up fabric realizuje sześć HPE Juniper QFX5252 z UALink over Ethernet.

**Znaczenie architektoniczne:** to materialny komercyjny sygnał, że rack-scale AI przestaje być wyłącznie domeną NVIDIA NVL72. Helios tworzy alternatywny, otwarty stack GPU+CPU+NIC+Ethernet scale-up, ale realne porównanie wymaga danych o collective latency, oversubscription, fault domains, power/cooling i dojrzałości ROCm. Dla capacity planning trzeba obserwować nie tylko GPU count, ale tempo delivery, fabric qualification i faktyczne job efficiency.

**Źródło:** https://www.hpe.com/us/en/newsroom/press-release/2026/09/hpe-secures-its-first-amd-helios-order-in-12-billion-deal-with-vultr.html

### Implikacje praktyczne

1. Przy planowaniu platform 2027+ uwzględniać AMD Helios jako realny wariant rack-scale obok NVL72/NVL144, ale wymagać workload-specific NCCL/RCCL, p99 i failure-domain testów.
2. Dla PQ migration planować równolegle key exchange i authentication/WebPKI; największe ryzyko operacyjne może leżeć w certificate ecosystem, nie w samym algorytmie.

4. Dla agentic security control plane wymuszać audytowalność źródła danych oraz human approval tam, gdzie AI może bezpośrednio zmieniać WAF/policy.

W obu przypadkach rośnie znaczenie poprawności control plane: błędna topologia albo błędnie zinterpretowany IOC może automatycznie pogorszyć zachowanie całej infrastruktury.

## AI for networking

### NVIDIA Topograph: scheduler dostaje zunifikowany obraz topologii fabric

- **Technologia / Zdarzenie:** NVIDIA Topograph — https://developer.nvidia.com/blog/topology-aware-workload-scheduling-with-nvidia-topograph/
- **Mechanizm działania:** provider odkrywa topologię z cloud API, InfiniBand `ibnetdiscover`, NetQ/Spectrum-X lub accelerator domains i normalizuje ją do wspólnego grafu. Engine generuje z niego konfigurację Slurm, Kubernetes labels, NFD resources, Slinky ConfigMaps albo topology JSON.
- **Wpływ na architekturę:** scheduler może lokować tightly-coupled jobs w najbliższym locality domain i ograniczać ruch przez współdzielone spine/core links. To szczególnie istotne przy wielodomenowych klastrach, MNNVL oraz środowiskach mieszających on-prem i neocloud.
- **Failure modes i edge cases:** stale topology jest groźniejsze niż brak topology-awareness, bo systematycznie kieruje joby do niewłaściwego failure/locality domain. Automatyczne refresh na node up/down nie wykrywa każdego switch rewire ani części zmian inventory, więc wymagane są okresowe pełne rediscovery, validation i rollback.

### MCP Python SDK: brak bindingu OAuth credentials do issuer umożliwiał credential exfiltration

- **Technologia / Zdarzenie:** GHSA-qx49-fqc8-xw99 — https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-qx49-fqc8-xw99
- **Mechanizm działania:** klient MCP ufał wskazanemu przez serwer authorization serverowi i nie wiązał zapisanych/pre-provisioned credentials z oczekiwanym issuerem. Złośliwy MCP server mógł skierować token request na własny endpoint i przejąć client_secret, authorization code, PKCE verifier lub signed client assertion.
- **Wpływ na architekturę:** MCP server jest częścią trust boundary auth, a nie tylko źródłem tools/resources. Przy centralnych agent gateways kompromitacja pojedynczego nieufnego serwera może skutkować przejęciem kont lub service identities o szerokich uprawnieniach.
- **Failure modes i edge cases:** szczególnie ryzykowne są shared gateways, stored registrations i private-key client auth. Poprawione wersje to 1.30.0 i 2.2.0; dodatkowo credentials powinny być issuer-bound i minimalnie scoped.

### Cloudflare Threat Signals: OSINT → IOC → WAF jako agentowy pipeline

- **Technologia / Zdarzenie:** Cloudflare Threat Signals — https://blog.cloudflare.com/threat-signals/
- **Mechanizm działania:** agentic skills czytają wybrane raporty/RSS, tworzą podsumowanie, wydobywają i normalizują IOC, tagują je istniejącym słownikiem konta i zapisują jako Threat Events. Te zdarzenia mogą następnie zasilać reguły WAF.
- **Wpływ na architekturę:** skraca to ścieżkę od threat reportu do egzekwowanej polityki i usuwa część ręcznego ETL. W dużym środowisku może istotnie obniżyć MTTR dla nowych kampanii, ale wprowadza model/agent do security control plane.
- **Failure modes i edge cases:** fałszywy IOC, błędna ekstrakcja kontekstu albo zatruty RSS może wygenerować złą blokadę. Krytyczne są provenance, ograniczony tag vocabulary, approval workflow i możliwość szybkiego rollbacku polityk.

## Newsletters summary

### MCP OAuth: nieufny serwer mógł przejąć credentials klienta

- **Technologia / Zdarzenie:** official MCP Python SDK, GHSA-qx49-fqc8-xw99.
- **Mechanizm działania:** brak walidacji issuer na wszystkich ścieżkach discovery oraz brak bindingu zapisanych credentials do konkretnego authorization servera umożliwiały redirect token requestu do atakującego.
- **Wpływ na architekturę:** przy agentach z szerokimi tool scopes MCP transport należy traktować jak element identity plane; serwer musi być ograniczony trust policy, a credential storage issuer-aware.
- **Failure modes i edge cases:** account takeover z uprawnieniami aplikacji, wyciek PKCE/client_secret/private-key assertions; wymagany upgrade do 1.30.0 lub 2.2.0.

**Źródło:** https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-qx49-fqc8-xw99

### Threat Signals: agent może zamienić raport OSINT w gotową regułę WAF

- **Technologia / Zdarzenie:** Cloudflare Threat Signals.
- **Mechanizm działania:** pipeline zachowuje powiązanie IOC z oryginalnym raportem i zapisuje wynik w prywatnym datasetcie konta; IOC może zostać użyty do budowy WAF policy.
- **Wpływ na architekturę:** security automation przesuwa się od feed ingestion do interpretacji nieustrukturyzowanych raportów, co może zwiększyć skalę pracy SOC bez proporcjonalnego wzrostu analyst headcount.
- **Failure modes i edge cases:** poisoning źródła, hallucinated indicator lub błędny kontekst mogą przełożyć się bezpośrednio na blokady produkcyjne; provenance i human approval powinny być zachowane.

**Źródło:** https://blog.cloudflare.com/threat-signals/

### Cloudflare PQ CA/MTC: PQ authentication bez eksplozji handshake size

- **Technologia / Zdarzenie:** Cloudflare public CA + Merkle Tree Certificates.
- **Mechanizm działania:** zamiast podpisywać każdy certyfikat osobno, CA podpisuje root append-only Merkle tree, a klient weryfikuje kompaktowy inclusion proof. To zmniejsza koszt przenoszenia znacznie większych podpisów PQ.
- **Wpływ na architekturę:** PQ WebPKI staje się wdrażalne bez proporcjonalnego wzrostu handshake/CT overhead; migracja wymaga jednak zmian po stronie root programs, browserów i CA.
- **Failure modes i edge cases:** root-store adoption, interoperability i operational complexity CA są krytyczniejsze niż sam benchmark handshake.

**Źródło:** https://blog.cloudflare.com/pq-ca-with-mtcs/
